# TDMA Terragraph 10.11 (Talyn) и что из него есть у Sparrow

Разбор `out3/tg_10.11.0.92_{fw,uc}` (имена — по строкам журнала), карта регистров `tg11_{fw,uc}.tsv`
(regmap.py), отбор TDMA-функций и их регистров — `tdm_regs.py` → `tdm_regs.tsv`. Стенд — 2026-10-23, .12
(open + отладочная WMI 0xfe0), STA к vendor AP .11. Метки: **[код]** — по декомпиляции TG 10.11,
**[стенд]** — проверено на Sparrow, **[гипотеза]**.

## 1. Слоты = аппаратный планировщик DTI/SP 802.11ad [код]

Диспетчер событий uc `FUN_15154` в цикле опрашивает биты регистра событий MAC `r54`:
- **бит 4 → квитирование `0x49000010` → `skip_sp_event_start(&0x8036f8)`** — оттуда все обработчики слотов:
  `handle_slot_start_event_missed_pre_slot`, `ucode_slot_control_handle_slot_end_event`,
  `fix_slot_indication / fix_late_start / fix_missed_full_slot / fix_slot_late_end`;
- бит 17 → `0x49020000` → `handle_gps_gpio_evt_isr` (импульс GPS);
- номер текущего слота — `0x886f8c` (`FUN_e6fc`); `0x886dd4` — биты 0..2 (звонок fw→uc).

Обработчики слотов к железу не обращаются: слот — это стандартное событие начала/конца SP аппаратного
планировщика DTI. У Sparrow то же самое: 6.2 квитирует r54 бит 4 (`0x49000010`) «для DTI-аллокаций»,
`HW_MAC_SCHED_SLOT_STATUS` 0x886f8c, включение планировщика — команда MAC 0x5a (rewrite uc/bi.c, bti.c),
регистры `HW_MAC_SCHED_SLOT_END/CTRL` 0x886f84/88, `MAC_EXT_SCHED_SLOT_START` 0x88c050.
**Вывод: механизм слотов TDMA Terragraph на Sparrow есть аппаратно** (планировщик SP), не хватает
программной части (расписание, переключение TX/RX по слотам, синхронизация узлов).

## 2. Метки времени кадров ~6 нс: 0x88c110…0x88c11c [код + стенд]

| регистр | TG 10.11 | Sparrow |
|---|---|---|
| 0x88c110 | `FUN_e6f0`, читает обработчик приёма `FUN_19398` | живой: TSF (мкс) последнего принятого кадра — растёт в простое каждые десятки мс, отстаёт от TSF 0x886eb8 на 10…60 мс **[стенд]** |
| 0x88c114 [7:0] | `FUN_e6e0`; × 0xecbe / 10000 | 0x15…0xa2 (≤ 164) — номер такта MAC 165 МГц внутри микросекунды **[стенд]** |
| 0x88c118 | `FUN_e730`, читает `FUN_1b730` после прямой передачи (`0x33000443`, `0x1d…`, ожидание `r47` бит 0 = `DIRECT_TX_CMD_STATUS`) | у vendor AP живой (маяки — прямые передачи ucode), у нашей STA — одно давнее значение **[стенд]** |
| 0x88c11c [7:0] | `FUN_e720`; × 0xecbe / 10000 | 0x71 / 0x74 |

Множитель 0xecbe/10000 = 6,0606 = 1000/165 — перевод такта MAC в нс. То есть пары дают время
приёма (ToA) последнего кадра и время передачи (ToD) последней прямой передачи с разрешением одного
такта MAC (6,06 нс). TG использует их для выравнивания времени узлов [гипотеза: синхронизация TDD].
**6.2, наша fw и драйвер этими регистрами не пользуются.** Кандидаты: синхронизация TSF узлов
mesh/TDD, FTM без блока ToF, измерение задержек.

## 3. Чего у Sparrow нет [стенд]

- **Захват TSF по импульсу GPS (PPS):** 0x88c754 (TSF) + 0x88c764 [7:0] (такт), `handle_gps_gpio_evt_isr`.
  У Sparrow от 0x88c500 чтение вешает чип — блока нет. Программная замена: прерывание GPIO + чтение TSF
  в обработчике (точность — задержка обработчика) [гипотеза].
- Регистры `mac_rgf_ext` TG 0x88c198, 0x88c1bc, 0x88c1d4 — у Sparrow 0xdeadbeaf.
- 0x8852xx/0x8854xx/0x8855xx/0x8856xx (PHY, `FUN_110d0`) и 0x886974 — 0xdeadbeaf.

## 4. Что ещё есть у Sparrow и не используется (TDMA-набор TG)
0x88c064 (поле [4:0] и [12:8] — кольцевой индекс, `FUN_1bbbc`), 0x88c10c (= 1 при работающем MAC,
пишет `hwd_mac_init`), 0x885194 (0x10101010), 0x88604c…58 (0xaaaaaaaa), 0x88401c, 0x8893f0.

## 5. Опыт 1: ToA/ToD подтверждены [стенд, 2026-10-23]
Данные — `sparrow_rgf/e1_toa_tod/`. BI = 102400 мкс (по шагу 0x886fc4 на обоих узлах).
- vendor AP .11: 0x88c118 — 20 из 23 значений в окне 1319,2…1320,8 мкс от начала BI (его маяк);
  наша STA .12: 0x88c118 меняется при её прямых передачах (3 значения под ping) — защёлкивает железо.
- STA: 0x88c110 обновляется на каждом принятом кадре (59 разных из 60 чтений в простое);
  после маяка — 1322,5…1327,5 мкс.
- Одновременный съём (одинаковое начало BI 0xb8984000 — TSF станции синхронизирован с AP): для 6 маяков
  ToA(STA) − ToD(AP) = 1,18; 1,30; 1,69; 1,76; 1,80; 2,44 мкс. Распространение ~1 нс; остальное — постоянная
  задержка тракта и дрожание синхронизации TSF (~1 мкс).
**Вывод:** 0x88c110 + 0x88c114[7:0]/165 — время приёма последнего кадра, 0x88c118 + 0x88c11c[7:0]/165 —
время последней прямой передачи; разрешение — такт MAC (6,06 нс).

## 6. Опыт 2: планировщик SP на vendor AP [стенд, 2026-10-23]
Данные — `sparrow_rgf/e2_sp/` (ese.bin — команда). WMI 0xa01 на .11 (vendor 6.2): флаги 9, одна аллокация
SP 0→1 (AP→STA), tbtt_offset 20000, duration 30000. Ответ 0x1a01.
- 0x886f8c на AP: 0 → 0x180 / 0x1c0 (планировщик включился; [3:0] = 0, биты 6–8 — состояние).
- iperf3 AP→STA: 965 → 727 Мбит/с.
- Фазы ToA у STA перестроились (сгустки 1,8–3,1 мс и 58–60,3 мс, провалы между), но данные AP не
  заперты в [20; 50) мс (26 % меток в окне против 29 % без расписания). Чтение «последней метки» с хоста
  раз в ~5 мс не восстанавливает границы окна — нужна плотная запись меток в uc.
- Снятие: перезапуск wifi на .11 (0x886f8c = 0) и перезагрузка .12 — связь восстановлена.

## 7. Опыт 3: гистограмма ToA в uc при SP на vendor AP [стенд, 2026-10-23]
Сборка toa.fw = open + poke + `UC_DBG=-DUC_TOA_HIST` (отладочный патч uc): `toa_poll`
в отдельном файле вызывается из главного цикла L1 и при смене 0x88c110 пишет фазу ToA в окно 0x853a00
(гистограмма 400 × 256 мкс + кольцо 64 точных фаз). Вставка в rx.c меняла кодоген соседних функций пути
ответа (межпроцедурно) — поэтому опрос из L1; по коду меняется только `l1_task_main_step`.
Данные — `sparrow_rgf/e4_toa_hist/`. iperf3 AP→STA 20 с.
- Без расписания: 42698 кадров, ~880 на 2 мс по всему BI (кроме BTI/A-BFT 0…4 мс), в [20; 50) — 30,4 %.
- SP 0→1 [20; 50) мс на vendor AP (0x886f8c = 0x1c0): 30904 кадра, 801 Мбит/с; плотность растёт плавно
  с ~21,5 до ~25 мс, **всплеск ×2,2 ровно в 49,66…50,18 мс (конец SP)**, повышена до ~57 мс, вне — ~65 %
  исходной. В [20; 50) — 37,2 %.
**Вывод:** vendor 6.2 как AP не запирает свои данные в SP (вне аллокаций — CBAP, CBAP Only = 1; ср. docs/ESE.md:
6.4 ставит 0); граница конца SP в железе видна (всплеск). Точность аппаратных границ SP по трафику vendor AP
не измерить — нужен наш AP, молчащий вне SP (аппаратная маска TX SP, docs/ESE.md §3).

## 8. Опыт 4: наша STA соблюдает SP из ESE — точные границы [стенд, 2026-10-23]
.12 = toa/toa2.fw (наша open + запись ToA), iperf3 STA→AP; ESE с vendor AP .11 (SP 0→1, [20; 50) мс).
Метки приёма у STA — BlockAck точки на передачу станции, то есть повторяют передачи станции.
- Планировщик STA включился сам по ESE из маяка: 0x886f8c = 0x14000110.
- Исход: 980 Мбит/с, ровно ~820 на 2 мс, 29,9 % в окне. С SP: 541…585 Мбит/с, в окне ~800 на 2 мс, вне — ~320
  (как в docs/ESE.md §3: 6.2 вне окон закрывает кольца хоста, а в SP, где узел только назначение, открывает кольцо
  к пиру — станция передаёт в SP точки, что 10.39.6.2 запрещает).
- Шаг 1 мкс (toa2.fw: участок задаётся poke 0x853e40/44): **конец SP — скопление меток 50,000…50,006 мс, затем
  ни одной до 50,060 мс**; **начало — первые BA на 20,125…20,128 мс** (~125 мкс: открытие кольца, DMA, A-MPDU,
  SIFS, BA). Граница окна исполняется железом с точностью единиц мкс относительно начала BI (0x886fc4).
Данные — `sparrow_rgf/e4_toa_hist/` (up_*, fine20/fine50).

## 9. Следующие опыты
1. Соблюдение 10.39.6.2 в нашей fw: точка — CBAP Only = 0 при ESE, передача только своих SP; станция — не
   инициировать в SP, где она только назначение (сейчас наоборот). Проверка — та же запись ToA.
2. Свой планировщик слотов поверх SP; синхронизация узлов по ToA/ToD.
3. Программная PPS-синхронизация по GPIO.
