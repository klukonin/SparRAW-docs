# 4. Прошивка и микрокод: протокол взаимодействия

В Sparrow два ARC-процессора: прошивка (fw, `fw_code` с 0x8c0000) ведёт
управляющую плоскость и общение с хостом, микрокод (ucode, `uc_code` с 0x920000)
— MAC в реальном времени ([глава 1](01-architecture.md)). Эта глава — обзор того,
как они разговаривают: почтовый ящик команд fw→ucode (LMAC), очередь событий
ucode→fw, табличные диспетчеры, автоматы `basic_sm` и ловушки адресации при
вмешательстве с хоста. Нижний уровень (команды ucode в MAC) — [глава 3](03-mac.md),
команды хоста WMI и UT — [глава 5](05-host-interface.md), различия версий —
[глава 8](08-versions.md).

Полный справочник протокола — [LMAC-PROTOCOL](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md),
автоматов — [STATE-MACHINES](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/STATE-MACHINES.md).
Пометки версий: **[4.1]**, **[6.2]**, **[обе]**.

> Коды LMAC (эта глава) и коды кольца MAC ([глава 3](03-mac.md)) — разные
> пространства; совпадение номеров (0x1e, 0x30) случайно.

## 4.1. Два процессора — два пространства 0x800000

Регистр `gp` задаётся один раз на процессор: **fw 0x800170** (инструкция на
0x8c0268), **ucode 0x800528** (на 0x9201b8) **[4.1]**; gp ucode 6.2 тот же. У fw и
ucode **разные** пространства данных 0x800000 — совпадение линкерных адресов между
ними ничего не значит.

| что | линкерный | host (debugfs `mem_addr`/`mem_val`/`mem_write`, `blob_*`) |
|---|---|---|
| данные fw (`fw_data`) | 0x800000..0x808000 | 0x900000 + (A − 0x800000) |
| данные ucode (`uc_data`, `blob_uc_data` 16 КБ) | 0x800000..0x804000 | **0x940000** + (A − 0x800000) |
| периферия fw (`fw_peri`) | 0x84xxxx/0x85xxxx | +0xc8000 |
| регистры MAC (`rgf`) | 0x88xxxx | без смещения |
| область `upper` | — | тождественно 0x8c0000..0x949000 |

Общий блок 0x857xxx (пишут обе стороны, напр. `0x857838` — запросы BF, `0x8577b8…`
— IE для TX FIFO) адресуется одинаково ([глава 1 §2.2](01-architecture.md)).

## 4.2. Транспорт: почтовый ящик fw↔ucode

* **Отправка [4.1]:** `send_cmd2_lmac(r0=buf, r1=cmd, r2=len, r3=extra)` @0x8e0694 →
  `basic_if__mailbox_send` @0x8e048c строит 16-байтовую шапку **ниже** буфера
  (`r13 = buf − 0x10`): +0x00 seq (из 0x803e3c), +0x02 len, +0x04 **код команды**
  (или тип события), +0x06 флаги, +0x08 `extra`, +0x0c TSF low, **+0x10 тело**.
  Звонок — `[0x886d80+0x58] = 1` (0x8e06f4), то есть ICS 0x886dd8 модели `RGF_ICR`
  ([глава 2 §3](02-registers.md)). **[6.2]:** `lmac_if__post_cmd` (`bl 0x8e5204`),
  объект ящика 0x804280.
* **Приём [4.1]:** `uc_mailbox__dispatch_one` @0x92a2b0 делает `add r2,r1,0x10` и
  зовёт `umac_if_cmd_handler(msg, body)`; обработчик получает указатель на тело в r0.
  События ucode→fw используют ту же шапку. **[6.2]:** `ucode_cmd_dispatch` @0x93c928;
  ucode держит свои кольца ящика (`uc_mailbox__init_rings` 0x9359b8,
  `uc_ring__init_desc` 0x92adf0) и проверяет место `mailbox__free_space` 0x92be30.
* **Трассировка на входе [обе]:** диспетчер обеих версий начинается с `ldw_s
  r0,[obj,0x4]` / `or r0,r0,0xcd0000` / `st.ab r0,[r25,4]` — каждая принятая
  LMAC-команда видна в журнале `blob_uc_data` как слово `0x00cd00NN`
  ([глава 3 §3.2](03-mac.md)).

Подробно — [LMAC-PROTOCOL §1](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#1-транспорт).

## 4.3. Команды fw→ucode

| | 4.1 | 6.2 |
|---|---|---|
| диспетчер | `umac_if_cmd_handler` @0x936dd0 | `ucode_cmd_dispatch` @0x93c928 |
| таблица | **байтовая** по 0x800c68 | **полусловная** по 0x8019dc |
| предел кода | 0x41 | 0x4a |
| база заглушек | 0x936e5e (байт × 2) | 0x93c966 (`ldw.x.as` + `add r0,pcl,0xa` + `add1_s` + `j_s`) |
| команд / разных обработчиков | 36 | 62 / 59 |

Ширину таблицы задаёт мнемоника: переход байт→полуслово — не смена компилятора,
таблица выросла. Таблица 4.1 строится автоматически (`tools/lmac_cmd_map.py`:
отправители — по константе в r1 у вызовов `send_cmd2_lmac`, обработчики — раскруткой
таблицы) и проверена шестью парами (0x0b, 0x25, 0x27, 0x39, 0x3a, 0x41) с независимо
известными именами. Полные таблицы команд обеих версий —
[LMAC-PROTOCOL §2](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#2-команды-fw--ucode).

Ключевые команды для биконинга и связи [обе]:

| код | смысл | тело |
|---|---|---|
| 0x00 | начальная конфигурация | +0x30 — тайминги IFS `fui_cmds_hw_cfg_ifs_timing_cfg_s` ([глава 3 §3.5](03-mac.md)) |
| 0x09 | запуск BF (`ucode_cmd_trigger_bf`) | `{1, bf_cmd_type, cid}` |
| 0x0b | конфиг биконинга (`ucode_cmd__bi_config`) | body+0x74 → 0x801438, `fui_bi_cfg_params_s`: +0x00 `bi_mode` (0 `BI_RX_BCON`, 1 `BI_TX_BCON`, 2 `BI_TX_DISCOVERY_BCON`, 3 `BI_TX_DIRECT_SINGLE_BCON` — «bcon_kind») |
| 0x10 | конфиг BF-автомата | `fui_cmds_bf_sm_mgmt_s` по body+0x24 (доказано поле `cid`) |
| 0x15 | personality | `fui_cmds_lmac_personality_s`: `LMAC_PASSIVE` = 1 (в нём `ucode_cmd_trigger_bf` @0x92226e не запускает BF) |
| 0x1e | CMD_SELECTIVE_NEIGHBOR_CFG | детекция/NAV/`short_txop_en` |
| 0x21 | пределы TXOP | → 0x886f70/74 |
| 0x23 | ответчик A-BFT | `fui_abft_resp_ctrl_s` → 0x802090/94/98 (0 UNASSOCIATED_ONLY, 1 ASSOCIATED_ONLY, **2 ALWAYS**, 3 DISABLED) |
| 0x24 | режим обнаружения (`ucode_cmd__discovery_mode_cfg` 0x934de4, «DISCOVERY ON/OFF») | |
| 0x25 | окно AW | |

Вендорские структуры тел (`fui_*`, пак 11ad) и их совпадение с 4.1 —
[LMAC-PROTOCOL §3](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#3-тела-команд-и-вендорские-структуры);
смысл полей для биконинга — [глава 6](06-beaconing.md), ответчик A-BFT —
[глава 7](07-beamforming-link.md). В 6.2 коды 0x28–0x4a в основном новые
(измерительные запросы, ToF/FTM/AoA, сектора TXSS, фиксированное расписание 0x3e,
триггеры PMC, заголовки очередей 0x45 — в 6.2 их пишет ucode, в 4.1 fw); код 0x06 —
встроенный фатал 0xa3
([LMAC-PROTOCOL §5.2](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#52-тела-команд-различающиеся-в-62-код)).

## 4.4. События ucode→fw

| | 4.1 | 6.2 |
|---|---|---|
| диспетчер fw | `lmac_if__ucode_event_dispatch` @0x8dae80 (индексация таблицы @0x8dae94) | `lmac_if__ucode_event_dispatch` @0x8df07c |
| таблица | полуслова по 0x801b98, тип ≤ 0x28 | полуслова по 0x801f40, типы 0..0x30 |
| база веток | 0x8daeb8 (значение × 2) | 0x8df0bc |
| именованных типов | 19 | 32 собственных ветви |

Каждая ветка печатает `Ucode-><ИМЯ>`, обработчик — первый вызов **после** логгера.
Главные типы [обе]: 0x00 UCODE_READY, 0x01/0x03 RX_ON/RX_OFF_RSP, 0x05 NEW_LINK,
0x06 BF_DONE, 0x09 LINK_LOST, 0x16 PS_AWAKE_PEER, 0x17 MAC_MONITOR (4 Б — указатель
на отчёт, из него BTI/AW/DTI), 0x27/0x28 get/set RF sector done
(`lmac_if__send_get/set_rf_sector_done`); последний тип 6.2 — 0x30
`EVT_FIXED_SCHEDULING_ENABLED`. Проверено живым логом: `Ucode->RX_ON_RSP : type 0x01`,
`PS_AWAKE_PEER_EVT: type 0x016`, `MAC_MONITOR_EVT: type 0x017`. Таблицы типов —
[LMAC-PROTOCOL §4](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#4-события-ucode--fw),
[§5.3](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#53-события-62).

**Очередь событий 0x802470 [6.2].** Буфер берётся из очереди
(`irq_safe__deref_field_04(0x802470)`), нагрузка копируется `memcpy_uc`, затем
`uc_evt__enqueue` (0x927958, 27 вызывающих; r1 — тип, r2 — длина; снимает TSF и
зовёт `uc_evt__queue_put` 0x9349dc). Обёртки `uc_evt__post_type6` (0x9275a8) и
`uc_evt__post_type5` (0x9276bc) кладут r0..r7 в буфер 0x44 байта и различаются одной
инструкцией (`mov r1,0x6` / `mov r1,0x5`). Отчёт по измерению собирает
`uc_evt__build_and_post_report` (0x93e624): 0x68 байт на стеке, тип 5 если тип кадра
равен 8, иначе 6; параметры — из контекста BF (0x802f28/2a/2c = +0x14..+0x18
структуры 0x802f14) либо из объекта, плюс TSF и адреса из 0x8020f0. Разметка
объекта — [UCODE-TASKS §3.7](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/UCODE-TASKS.md#37-0x802470--сборка-сообщения).
Путь «связь потеряна» из ucode на стенде не срабатывал — LOST_LINK приходит от
детекторов fw ([UCODE-TASKS §2.1](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/UCODE-TASKS.md#21-путь-связь-потеряна-из-ucode-код--железо)).

## 4.5. Протокол не менялся между 4.1 и 6.2

* **Механизм тот же** — команда в объекте, код полусловом по +4, трассировка
  `код | 0xcd0000` в журнал, события — слот очереди с типом и длиной.
* **Номера совпадают** — все 36 команд 4.1 есть в 6.2, все 19 типов событий — под
  теми же номерами; обёртки отправки событий совпадают даже размерами блоков
  (44/44/32/68 байт), что позволило перенести имена по коду типа.
* **Изменилось**: ширина таблицы команд (байт → полуслово), команд 36 → 62,
  событий 19 → 32 ветви, адреса диспетчеров.

Уровнем ниже пространство кодов кольца MAC тоже идентично (77/77,
[глава 3](03-mac.md)), тулчейн тот же; при этом дословно общего кода между версиями
лишь 11–12 %. Размер таблицы — не число команд: в 4.1 из 66 записей 30 ведут в
общую заглушку, в 6.2 из 75 — 13; дырки в середине диапазона (0x0a, 0x0d, 0x0e,
0x17, 0x1a, 0x1c, 0x1d, 0x1f — в обеих версиях) — зарезервированные или выпиленные
коды ([LMAC-PROTOCOL §5](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/LMAC-PROTOCOL.md#5-различия-41-и-62)).

## 4.6. Табличные диспетчеры

Таблицы диспетчеризации — главный источник точных имён: они дают соответствие
«код — функция», и каждая расшифрованная таблица попадает несколькими ячейками на
ранее названные функции (самопроверка). **Образец поиска:** загрузка индекса из
таблицы в данных, затем `add rX,pcl,N` и `j [rX]`, **а в ветке — `bl`**; без
последнего это обычный `switch` внутри функции (29 из 69 найденных)
([COVERAGE-CENSUS-4100](../research/COVERAGE-CENSUS-4100.md)).

| диспетчер | версия | таблицы | что |
|---|---|---|---|
| `umac_if_cmd_handler` @0x936dd0 (uc) | 4.1 | 0x800c68 (байты) | команды LMAC |
| `ucode_cmd_dispatch` @0x93c928 (uc) | 6.2 | 0x8019dc (полуслова) | команды LMAC, 59 обработчиков |
| события ucode @0x8dae94 (fw) | 4.1 | 0x801b98 | 19 типов |
| `lmac_if__ucode_event_dispatch` @0x8df07c (fw) | 6.2 | 0x801f40 | типы 0..0x30 |
| WMI (`host_if__wmi_cmd_dispatch`) @0x8da60c (fw) | 4.1 | 0x801bec + подтаблицы | команды хоста |
| WMI (`wmi__host_cmd_dispatch`) @0x8de394 (fw) | 6.2 | — (4 208 байт) | команды хоста, имя из строки «---->> [HOST CMD] WMI_…» |
| `UT_HW_DRIVERS_cmd_handler` @0x8e5be8 (fw) | 4.1 | 0x803124, 0x80332c, 0x803374, 0x80339c | 146 обработчиков |
| `UT_HW_DRIVERS_cmd_handler` @0x8eaec8 (fw) | 6.2 | девять таблиц 0x8039f4..0x803b54 | подкоманды драйверов |
| `UT_HW_MODES_cmd_handler` @0x8e6f24 (fw) | 4.1 | 0x802f24 | 18 |
| `UT_HW_FLOWS_…BER_TEST` @0x8e66d8 (fw) | 4.1 | 0x802d6c, 0x802d88 | 21 |
| `conn_mgr`/`POWER_MNGR::system_state_evt_handler` (fw) | 4.1 | 0x801e4c, 0x8018b4 | по номеру события из 0x800fbc |
| `background_task__dispatch` @0x921e2c (uc) | 4.1 | 0x800ba0 (5 байт) | фоновые задания по битам 0x800630 |
| `internal_tx_isr` (uc) | 6.2 | 0x801a94 (байты) | потоки внутренней передачи |

Байтовые `switch` в 6.2 тоже есть (0x801a94, 0x8017e0). Команды WMI и UT —
[глава 5](05-host-interface.md),
[WMI](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/WMI.md),
[UT-DRIVERS](https://github.com/klukonin/SparRAW-firmware/blob/main/6.2/docs/UT-DRIVERS.md).

Правила:

* **Логгеры исключать из карты «строка → обработчик»**: строку печатает логгер,
  обработчик — следующий вызов за ним. Логгеры 6.2: fw
  0x8dcba8/0x8dcc10/0x8dcc80/0x8dcd00 = `fw_log_emit0..3`, uc
  0x92d13c/0x92d1d0/0x92d27c/0x92d338 = `uc_log_emit0..3` (число аргументов доказано
  подсчётом `%` во всех вызовах); без этого вся карта WMI указывала на 0x8dcba8.
* **Имя из таблицы годится, только если у функции один-два вызывающих**: под
  `conn_mgr_on_enable_ps_mode` стоит утилита с 86 вызывающими. Часть UT-целей 4.1
  поэтому осталась без имени по коду команды — соответствие живёт в таблице
  [UT-COMMANDS](../research/UT-COMMANDS.md).
* **Имена UT из пака 11ad не переносить без проверки**: нумерация wil6436 совпадает
  со Sparrow лишь частично (совпало 7, расходится 8).
* Адрес таблицы диспетчера не ставить в комментарий обработчика (ревизия дала 42
  ложных замечания по «заглушке N таблицы 0x8019dc»).
* Другие точки косвенного вызова в fw — `u_schd__schedule` @0x8dc92c и
  `u_schd__add` @0x8c2ac8 (4.1; 6.2 — 0x8e0c0c и 0x8c3248, плюс `u_schd__cancel`):
  первый аргумент — **адрес колбэка минус 0x8c0000**, задержка в r4 (делится на 16 и
  складывается с `fw_read_timer`)
  ([SCHEDULER](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/SCHEDULER.md)).

## 4.7. Автоматы `basic_sm`

Все автоматы прошивки и микрокода — на общем движке `basic_sm`. Запись таблицы
переходов — **5 байт** (4 байта обработчика + байт следующего состояния), индекс =
**состояние + событие × n_состояний**; разбор повторяет `basic_sm__inject_event`
@0x8d6a1c («Inject %s event to %s. Next state: %s»).

* **[4.1]** `basic_sm__setup` @0x8d6478 получает `(obj, имя, нач.состояние,
  таблица, имена_событий, n_событий, имена_состояний, n_состояний)` в r0…r7 и пишет
  их в объект (+0x18 таблица, +0x1c/+0x20 имена, +0x24 имя автомата). **21 автомат**,
  имена — массив указателей 0x800150…0x8001d8; выгрузка `ref/SM-TABLES.txt` дерева
  4.1 (`tools/sm_tables.py`). Таблицы дают 72 имени обработчиков и границы 35
  блоков; по ним блок @0x8ed454 — `mlme_sm__init` (не `conn_main_sm__init`),
  @0x8d5a0c — `sta_psc_sm__init` (не `psc_sm__init`).
* **[6.2]** таблицы вынесены в **описатель** 20 байт (адрес в r1): +0 число
  **событий**, +1 число **состояний**, +2 начальное состояние, +4 таблица, +8 имена
  состояний, +12 имена событий; привязка — `basic_sm__bind_descriptor` fw 0x8d94e0,
  uc 0x92af0c. В записи таблицы вместо адреса — смещение обработчика от базы
  сегмента кода. Перестановка +0/+1 даёт тихую ошибку (пары «событие в состоянии»
  неверны; признак — массив имён состояний продолжается именами событий); контроль —
  `mlme_sm` (0x802458: 14 событий, 3 состояния). Имя автомата — общий префикс имён
  состояний, иначе голосование по названным обработчикам без общих заглушек.
  **24 автомата в fw** (выгрузка
  [`6.2/ref/SM-TABLES.txt`](https://github.com/klukonin/SparRAW-firmware/blob/main/6.2/ref/SM-TABLES.txt)).
  Графы переходов двух сборок 6.2 разных производителей идентичны по next-state в 14
  из 15 сопоставленных автоматов; шесть автоматов энергосбережения вырезаны в сборке
  UBNT ([UBNT-vs-ROUTEROS-6.2](../research/UBNT-vs-ROUTEROS-6.2.md)).
* **Автомат микрокода** — единственный, интервала маяка: [4.1] `BI_AP_MONITOR_SM`
  (объект 0x801de8, движок @0x9287ec, таблица 0x800adc, `bi_ap_mon__init` @0x928130);
  [6.2] `bi_sm` (описатель 0x801adc, 4 × 5, старт BI_STATE_DTI, шаг
  `uc_sm__handle_event` 0x92b6fc). Состояния 0 BTI, 1 ABFT, 2 DTI, 3 AW; события
  0 DTI_TO_BTI, 1 BTI_TO_ABFT, 2 BHI_TO_DTI, 3 BHI_TO_AW, 4 AW_TO_DTI [обе]. Кто подаёт

## 4.8. Таблицы диспетчеризации ucode в ОЗУ

В ucode 4.1 часть таблиц переходов и обработчиков **заполняется в рантайме**, в
образе их нет; поэтому Ghidra из 13 адресов BI-автомата знала функциями только 4.
Приём: снять `blob_uc_data` с живого узла
(`/sys/kernel/debug/ieee80211/phy0/wil6210/blob_uc_data`, 16 КБ = 0x800000…0x804000),
найти слова `v`, для которых `0x920000 + v` попадает в код ucode и уже
дизассемблирован по потоку, и оформить там функции. Итог: 114 кандидатов, 43 вне
любой функции, создана 31 функция
([COVERAGE-CENSUS-4100](../research/COVERAGE-CENSUS-4100.md)). **На стороне fw приём
не работает**: в `blob_fw_data` один абсолютный указатель на код из 542 кандидатов —
таблицы fw лежат в образе данных, многие ветвления идут цепочками сравнений.

Так же только в ОЗУ существуют структуры состояния за концом образа `uc_data`:
0x802ec0 (счётчики окон BI, 6.2, образ 7 144 Б) и `bcon_kind` 0x801438 (4.1, образ
3 828 Б, BSS).

## 4.9. Ловушка адресов `mem_write`

`wmi_addr_remap` в драйвере ищет область с флагом **`fw == true`**, а
`uc_code`/`uc_data` в `sparrow_fw_mapping` помечены `fw = false`. Поэтому линкерный
адрес ucode, например **0x801438**, матчится на `fw_data` и превращается в
**0x901438 — данные прошивки**: запись молча портит чужую переменную. Правильно —
host-адрес `0x940000 + (линкерный − 0x800000)`, попадающий в тождественную область
`upper`.

| переменная ucode | линкерный | host |
|---|---|---|
| `bcon_kind` / `bi_mode` | 0x801438 | 0x941438 |
| период BI, мкс | 0x801434 | 0x941434 |
| ответчик A-BFT (LMAC 0x23) | 0x802090/94/98 | 0x942090/94/98 |
| счётчики окон BI (6.2) | 0x802ec0 | 0x942ec0 |

Запись `0x941438 = 2` открывает гейт рандомизатора — кольцевая команда 0x30 идёт со
значениями в [10, 198] **[4.1, железо]**
([BEACONING §9.1](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/BEACONING.md#91-открытие-гейта-с-хоста-41-железо)).
После записи значение перечитывается `mem_val` или `blob_uc_data` по тому же
host-адресу. Смежные ловушки: поле, которое ucode перезаписывает сам (0x886d64 при
рестарте цикла), затирается; порт команд MAC 0x886dc8 с хоста хранит слово, но не
исполняет его ([глава 3 §3.2](03-mac.md)); сброс прошивки перевзводит уровни лога
драйвером и затирает ручную маску.

## 4.10. Расхождения источников и открытые вопросы

1. **Массив имён автоматов 4.1**: 0x800150…0x8001d8 (21 автомат, выгрузка таблиц)
   против 0x800150…0x8001d4 («20 штук», перепись покрытия
   [COVERAGE-CENSUS-4100](../research/COVERAGE-CENSUS-4100.md)).
2. **LMAC 0x30** в 4.1 и 6.2 выглядит по-разному (`{idx, bit, val7}` против «RS
   start/abort», `ucode_cmd_0x30_handler_uc` 0x92ff04); источники расхождение не
   обсуждают. К кольцевой команде MAC 0x30 (задержка маяка) отношения не имеет.
3. **Не установлено:** смысл команд 0x04, 0x07, 0x11, 0x16, 0x19, 0x1b в 4.1;
   отправитель 0x26 в 6.2; содержимое таблиц, заполняемых `boot__install_handler_ptrs`
   в 6.2; имена типов событий 6.2 сверх общих 19.
