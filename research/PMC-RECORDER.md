# Регистратор пакетов MAC (PMC): сниффер на самом узле

Стенд — два wAP 60G (Sparrow), board lowpwr3 на обоих узлах; прошивка — образ SparRAW (точка и станция), часть
прогонов — станция SparRAW к точке vendor 6.2. Опыты 2026-11-03…04. Драйверная часть (кольцо, разбор, Radiotap,
интерфейс `wilmon<N>`) — в SparRAW-driver (`capture.c`, `pmc.c`, `tools/pmc_decode_test.py`), подробное описание —
`rewrite/docs/CAPTURE.md` в SparRAW-firmware. Что MAC делает в эфире по этим записям — [MAC-AIR-TIMING](MAC-AIR-TIMING.md).

Пометки доказанности: **[эфир]** — видно в записях PMC на стенде; **[стенд]** — опыт или счётчик на железе без
записи; **[пак]** — по vendor debug-tools; **[код]** — по коду; **[гипотеза]**.

## Итог

* PMC — аппаратный блок MAC со своим DMA-кольцом (кольцо 7) в памяти хоста. Пишет поток записей о своих и принятых
  кадрах без участия fw и ucode: fw только выделяет кольцо (`WMI_PMC` 0xf04f, есть и в vendor fw), остальное —
  регистры PMC с хоста. Точка или станция при записи работает как обычно.
* **TX**: пишутся все свои кадры — SSW, SSW-Feedback, SSW-Ack, RTS, DMG CTS, BlockAck, CF-End, кадры управления,
  QoS Null; кадры данных — только с битом qos в TX-маске **[эфир]**.
* **RX**: байты пишутся только у кадров, которые MAC отдал в очередь (маяки и кадры управления для fw, данные для
  хоста). Ack, BlockAck, RTS, DMG CTS, CF-End, SSW пира и чужие кадры в очередь не идут — их байтов нет. Но о
  **каждом** принятом PPDU пишутся записи `a7` (TSF, длина, MCS) и `af` (отчёты MAC r36..r39), по ним тип кадра,
  передатчик и «кадр нам» восстанавливаются **[эфир]**.
* Точка метки TX у маяка совпадает с полем Timestamp (17 802 из 17 802) **[эфир, 2026-11-04]**.
* Ограничения железа: у ответов, которые MAC шлёт сам, метка времени TX бывает испорчена (2 или 6 вместо TSF);
  последний байт TA в принятых кадрах заменён (0 или номер соединения пира); записи кадров данных под тяжёлой
  передачей вешают узел **[эфир / стенд]**.

## 1. Регистры (Sparrow, окно RGF, адреса 1:1)

Карта — vendor debug-tools (`PmcRegistersAccessor.cpp`, ветка `BASEBAND_TYPE_SPARROW`) **[пак]**; значения пуска —
по `PmcSetConfigHandlerSequences.cpp` и опытам на стенде 2026-11-03 (запись через `mem_write`, связь не страдала,
FWERR 0).

| адрес | имя | поля |
|---|---|---|
| 0x88607c | `PMC_CTL` | [15:0] разделитель записей (0xcafe); б16 `rec_en_set`, б17 `rec_en_clr`, б18 `rec_active` (чтение), б24 `rx_en`, б25 `tx_en`, б26 `ucode_event_en`, б27 `idle_sm_en` |
| 0x886080 | `PMC_IF_CFG` | 0x01000005: б0 тип интерфейса = 1, б2 DMA = 1, [27:16] порог 256 (смысл порога не установлен) |
| 0x88608c | `PMC_CFG_8C` | 0xfc, как у vendor; смысл не установлен |
| 0x886094 / 0x8860ac | `PMC_RX_QID` / `PMC_TX_QID` | маска очередей = 1 |
| 0x886098 | `PMC_RX_MASK` | б0 qos, б1 mgmt, б2 control, б3 beacon, б4 error, б5 phy |
| 0x88609c / 0x8860a0 | `PMC_RX_MAXD0/1` | предел байт записи RX в двойных словах, байт на тип: 0x88609c — типы б0..б3, 0x8860a0 — б4..б5 |
| 0x8860b0 | `PMC_TX_MASK` | б0 qos, б1 mgmt, б2 control, б3 beacon, б4 direct |
| 0x8860b4 / 0x8860b8 | `PMC_TX_MAXD0/1` | то же для TX: типы б0..б3 и б4 |
| 0x886200 | `MAC_PRS_CTRL_0` | б16 `pmc_post_dec_mode` (vendor ставит на время записи) |
| 0x8815ec | IS кольца 7 | б6 `is_pmc_dma` (ставит fw) |
| 0x8815f8 | `PMC_RING_SW_TAIL` | последний индекс, отданный аппаратуре |
| 0x881620 | `PMC_RING_SW_HEAD` | позиция записи аппаратуры **[гипотеза]** |

Единица предела — двойное слово **[стенд]**: 8 → 32 Б, 0x40 → кадр данных 222 Б целиком; длина записи — один байт,
поэтому предел не больше 63 (252 Б). Порядок типов по байтам регистров предела — **[гипотеза]**. Тактирование PMC
(0x880c20 б9) включает уже запись direct_write образа vendor.

Пуск: 0x886080, 0x88608c, очереди, маски, пределы, б16 0x886200; затем `PMC_CTL` = 0x0300cafe (`rx_en`, `tx_en`) и
0x0301cafe (`rec_en_set`). Останов: 0x0000cafe, пауза 1 мс (PMC сбрасывает свой буфер в DMA), 0x0002cafe
(`rec_en_clr`) и ожидание снятия б18, затем вернуть б16 0x886200.

## 2. Кольцо 7

* Дескрипторы — формат `vring_tx_desc` (32 Б), без `DMA_IT` (иначе ложные прерывания RX_DONE). fw по `WMI_PMC` op 0
  ставит базу, размер, `SW_TAIL` = d − 1, б6 IS и номер кольца 7 в `PRP_CTRL[11:8]`; op 1 — сброс очереди 7.
  Прерываний нет, кольцо опрашивается.
* **Поток байтов непрерывен**: аппаратура заполняет буферы целиком и подряд, записи переходят через границу буфера
  **[эфир]**.
* **DU — не признак готовности буфера [стенд, 2026-11-03]**: DU стоит, а вторая половина буфера ещё не записана
  (в данных — заполнитель, которым буфер был заполнен при возврате); аппаратура дописывает её позже, в уже
  возвращённый буфер. Готовность надо определять по данным: записано последнее слово буфера или первое слово
  следующего.
* Аппаратура пишет до `SW_TAIL` − 1 (один буфер — зазор). Буфер может быть закрыт не до конца (запись обрывается,
  поток продолжается в следующем).

## 3. Формат записей **[эфир]**

Little endian. Запись: `fe ca LEN TYPE` + LEN байт, дополнение нулями до 4 Б. Разделитель — младшие 16 бит
`PMC_CTL`.

**TX** (свой кадр):

| тип | LEN | данные |
|---|---|---|
| 0x55 | 0 | начало группы |
| 0x56 | 4 | u32 длина MPDU с FCS |
| 0x57 | ≤ предела | MPDU без FCS, с Frame Control |
| 0x58 | 0 | конец |
| 0x59 | 12 | u32 TSF[31:0] мкс, затем два слова сведений (например 0x0680, 0x0500; смысл не установлен) |

Группа `55 58 59` без `56/57` — свой кадр типа, не включённого в TX-маску.

**RX**:

| тип | LEN | данные |
|---|---|---|
| 0xa7 | 8 | u32 TSF[31:0] мкс; u32: [..:6] длина PSDU с FCS, б5 ?, [4:0] DMG MCS (у A-MPDU — длина PSDU) |
| 0xa8 | 4 | u32 длина PSDU/MPDU с FCS |
| 0xab | ≤ предела | байты MPDU; при полной длине последние 4 Б — **не CRC-32** (не совпало ни в одном кадре), а слово вида 0x00XXXXXX |
| 0xae | 4 | u32 статус (0, 0x0a00, 0x0100) |
| 0xaf | 24 | w0 статус PMC (б16 — PPDU **не** отдан в очередь), w1 ?, w2..w5 — отчёты MAC r36, r37, r38, r39 |

`a7 af` и `a7 ae af` без `ab` — PPDU, не отданные в очередь; это основная масса записей (на дампе 5 с — 3416 таких
групп против 176 кадров с байтами).

## 4. Отчёты r36..r39 в записи `af` **[эфир, 2026-11-03…04]**

Те же слова uc читает как отчёт о последнем PPDU (группы r36..r39 `MSXD_LR_RGF`,
[02-registers §5](../chip/02-registers.md)).

| слово | поля |
|---|---|
| r36 | б1 QoS Data, б3 — кадр RTS/DMG CTS, б9 BlockAck (0x201 у BlockAck), [23:19] `data_frame_qid` (очередь данных); 0x203 — BlockAck вместе с данными (ответ reverse direction) |
| r37 | б0 RTS, б1 DMG CTS, б16 CF-End, б24 SSW, б25 SSW-Feedback, б26 SSW-Ack |
| r38 | [10:8] номер соединения (CID) передатчика, б11 — номер верен; б12 `bap_enable`; б15 `reverse_direction_detected` (RDG в принятом PPDU, [MAC-AIR-TIMING §6](MAC-AIR-TIMING.md)); [17:16] `requested_ack_policy`; [24:20] MCS (= `a7`[4:0] на всех кадрах); б25 агрегация (A-MPDU); б28 — сосед (кадр не нам); б29, б30 — FCS в порядке; б31 — отчёт верен |
| r39 | [13:8] **слот таблицы 3 парсера** — тип кадра (§5); б15 — CDOWN = 0 у SSW (стоит и у части RTS — смысл шире); б27 — адрес получателя совпал (кадр нам) |

Примеры: BlockAck — r36 0x201, r38 0xe0101800, r39 0x08001840; DMG CTS нам — r37 0x2, r39 0x0801b340; DMG CTS не
нам — r38 0xf0000000, r39 0x00013380; RTS — r37 0x1, r39 0x08001a40.

## 5. Таблица 3 парсера: слот = тип кадра **[эфир + стенд]**

Слот r39[13:8] — номер правила таблицы 3 парсера MAC (64 слота, поиск по Frame Control, как CAM). Правило — два
слова; w0[9:0] — ключ FC[11:2] (FC = ключ << 2). Правила прочитаны на стенде 2026-11-03 (35 непустых); ключи
сверены с IEEE 802.11-2020 Table 9-1 и 9-2 (control frame extension: type 1, subtype 6, FC[11:8] — номер
расширения).

| слот | кадр (FC, LE u16) |
|---|---|
| 0x00 | DMG Beacon (0x000c) |
| 0x01..0x0c | Assoc Req 0x0000, Assoc Resp 0x0010, Reassoc Req 0x0020, Reassoc Resp 0x0030, Probe Req 0x0040, Probe Resp 0x0050, Beacon 0x0080, ATIM 0x0090, Disassoc 0x00a0, Auth 0x00b0, Deauth 0x00c0, Action 0x00d0 |
| 0x0f | Action No Ack (0x00e0) |
| 0x10 | Grant Ack (0x0764) |
| 0x17..0x1c | BAR 0x0084, BlockAck 0x0094, PS-Poll 0x00a4, RTS 0x00b4, CTS 0x00c4, Ack 0x00d4 |
| 0x2c | QoS Null (0x00c8) |
| 0x30..0x34 | Poll 0x0264, SPR 0x0364, Grant 0x0464, DMG CTS 0x0564, DMG DTS 0x0664 |
| 0x35 | CF-End (0x00e4) |
| 0x36..0x38 | SSW 0x0864, SSW-Feedback 0x0964, SSW-Ack 0x0a64 |
| 0x3c..0x3f | QoS Data: 0x0088, To DS 0x0188, From DS 0x0288, оба 0x0388 |

Остальные слоты пусты. По слоту, длине из `a7`, CID из r38 и б27 r39 драйвер строит кадр-заготовку (FC, RA, TA,
длина; Duration и тело не известны) для PPDU без байтов.

## 6. Особенности и ограничения

**Последний байт TA в принятых кадрах заменён [эфир].** Во всех принятых кадрах (DMG Beacon — BSSID, кадры
управления и данные — A2) последний байт адреса передатчика записан как 0: `24:18:1d:24:3b:00` вместо
`…:3b:0b` точки; A1, A3 и все адреса своих TX-записей верны. Байт совпадает с CID передатчика (у станции CID
точки = 0, поэтому «0» и «CID» на стенде с одной станцией не различить). Вероятная причина — запись кадра после
поиска адреса в таблице пиров (б16 `pmc_post_dec_mode` 0x886200) **[гипотеза]**; проверки — запись без б16 и точка
с несколькими станциями (CID ≠ 0). Так же у маяка RX-запись станции отличается от TX-записи точки ещё в октете 25.

**RDG в байтах приёма стёрт [эфир, 2026-11-04].** В RX-записях бит RDG/More PPDU поля QoS Control = 0 у всех
кадров, в том числе у A-MPDU, которые TX-запись передатчика показывает с RDG = 1; признак RDG — r38 б15 (1 у
1795 из 1809 A-MPDU станции на точке и у 1981 из 1998 A-MPDU точки на станции, 0 у ответов RD). Судить о RDG
по байтам принятого кадра нельзя.

**Метка TX у ответов MAC [эфир, 2026-11-04].** У кадров, которые MAC шлёт сам (Ack, немедленный BlockAck, DMG CTS
на RTS, CF-End, RTS, SSW, ATIM), вместо TSF в `59` бывает 2 или 6: точка SparRAW под iperf — 87 762 из 249 834
TX-записей (BlockAck с `info0` 0x804 — 2, прочие — 6); станция в одном прогоне — 7412, в другом — ни одной. От чего
зависит — не установлено. Такие метки надо отбрасывать (иначе время откатывается на десятки секунд).

**Записи кадров данных вешают узел [стенд, 2026-11-04].** С битом qos в RX- и TX-маске точка под нисходящим iperf
~950 Мбит/с повисла целиком за секунды (ни ping, ни netconsole — похоже на остановку шины). Без записей данных та
же точка держит 985 вниз / 910 вверх Мбит/с, записано 74 940 TX-записей control/mgmt без потерь. Записи данных —
только без тяжёлой передачи. У станции с битом qos в TX-маске TX-записей данных не было (у точки были) — не
разобрано.

**Метка — какая точка PPDU.** У маяка метка TX = поле Timestamp (11.1.3.1: начало символа данных с первым битом
кадра) **[эфир]**; абсолютная точка без внешнего эталона времени не проверена. Метки TX и RX одного PPDU стоят не в
одной точке, сдвиг зависит от класса модуляции: RX − TX = −1,58 мкс (control PHY) / −0,12 мкс (SC) по парам
одинаковых кадров обоих узлов **[эфир, 2026-11-04]**.

**TSF двух узлов.** Станция принимает TSF точки; по парам TX↔RX одного PPDU TSF станции **отстаёт** от TSF точки на
~2,9 мкс (медиана 2,58…3,58 по окнам, 102 окна) **[эфир, 2026-11-04]**. Записи двух узлов сводятся в одну шкалу
этим сдвигом.

## 7. Почему не vendor-режим sniffer

`WMI_CFG_RX_CHAIN.sniffer_cfg` перестраивает RX-очереди MAC и канал и останавливает маяк — узел перестаёт быть
точкой/станцией. PMC пишет параллельно обычной работе.
