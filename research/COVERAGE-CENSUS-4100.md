# Атрибуция кода 4.1.0.1000: проверенные правила и динамическое покрытие

Какие правила привязки безымянных функций к исходным файлам и именам выдерживают
проверку на отложенной выборке, какие отвергнуты, и что показывает покрытие по
факту исполнения. Итоговые имена и карта файлов — в дереве прошивки
(`4.1/ref/FN-NAMES.txt`, `4.1/ref/NAMES-EXTRA.txt`, `4.1/ref/FN-FILEMAP.txt`);
табличные диспетчеры и поиск таблиц ucode в ОЗУ —
[../chip/04-fw-ucode.md §4.6](../chip/04-fw-ucode.md);
милли-код и значения `gp` —
[docs/TOOLCHAIN.md](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/TOOLCHAIN.md),
[docs/FW-UTILITIES.md](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/FW-UTILITIES.md).

## 1. Границы счёта

Программа Ghidra по сегменту 0x8c0000 содержит код двух процессоров:

| область | адреса |
|---|---|
| `fw_code` | 0x8c0000…0x900000 |
| ucode | 0x900000…0x949000 |

Проценты по всему сегменту и по одному `fw_code` несравнимы. В дереве исходников
знаменатель однозначен: все байты сегмента, разбитые на блоки по границам функций
(`fw_code` 2527 блоков / 211 800 Б, `uc_code` 709 / 98 500 Б).

## 2. Правила атрибуции на отложенной выборке

Метод: спрятать 20 % функций с привязкой по ассертам (эталон, 392 функции),
предсказать их файл по остальным, повторить 5 раз.

| правило | предсказано | верно |
|---|---|---|
| соседство: функция между двумя функциями одного файла | 116 | **108 (93 %)** |
| граф вызовов, ≥ 2 согласных вызывающих | 14 | 6 (43 %) |
| граф вызовов, ≥ 1 вызывающий | 100 | 33 (33 %) |
| ровно 1 вызывающий | 39 | 12 (31 %) |
| ровно 1 вызывающий, и он привязан | 33 | 10 (30 %) |
| ≤ 2 вызывающих, все согласны | 47 | 20 (43 %) |
| файл как у предыдущего блока | — | 63 % (fw), 59 % (uc) |
| файл как у единственного вызывающего (по дереву) | — | 27 % (fw), 38 % (uc) |

Принято только соседство. Граф вызовов для атрибуции файла непригоден:
компоновщик не кладёт вызываемое рядом с вызывающим, статические помощники
вызываются через границы файлов. Роль («участвует в развёртке маяка») по
специфичному вызывающему выводить можно, файл — нельзя.

Отвергнуты также:

* **Положение строки в таблице строк.** Строки лежат в порядке компиляции, имена
  файлов — разделители. Без имени файла в уликах: ≥ 1 строка — 71 %, ≥ 2 и все
  согласны — 76 %, ≥ 3 — 82 %. Где правило согласно с соседством — 20 из 20, но
  это подмножество соседства; при споре правило строк проигрывает (соседство
  право в 4 из 7). Самостоятельной ценности нет.
* **Перенос имени между блоками одинаковой формы** (≥ 8 инструкций): в группах с
  известными именами однокоренные имена лишь в 6 из 23 — одинаковая
  последовательность мнемоник отражает почерк компилятора на мелких функциях
  программирования регистров, а не назначение.
* **Номер модуля лога** (биты 20…23 заголовка записи): связка «строка → модуль» по
  74 живым захватам (1018 строк) даёт подсистему функции; 12 файлов из 13
  получают ровно один модуль (исключение — `lmac_if.cpp`, четыре модуля). Новых
  функций правило не даёт: всё, что пишет в лог, уже названо по строкам.
  Годится для перекрёстной проверки.
* **Имя из таблицы диспетчера** надёжно лишь при одном-двух вызывающих: под
  ячейкой таблицы может оказаться общая утилита (0x8c1a78, 86 вызывающих),
  попавшая туда как хвост ветки.

Работает **привязка по структурам данных**: функция, обращающаяся к базе
известной структуры (отчёт MAC_MON 0x854de0, кольцо лога 0x843900, конфигурация
BI 0x801438, `bi_manager` 0x801e94, автомат BI 0x801de8, `POWER_MNGR` 0x801ed0,
таблицы расписания), относится к её подсистеме; так опознаны, в частности,
`bi_ap_mon__bti_event` и `bi_window_timing_update`.

## 3. Код вне функций

Байты, не входящие ни в одну функцию, не попадают даже в знаменатель: в
`fw_code` их было 46 120 Б (22 % сегмента) в 1072 кусках, в ucode — 4 576 Б.
Кусок 0x8da512 (3150 Б) разбирается в 949 инструкций без единого
неразобранного байта, с вызовами, `push_s blink`, обращениями к милли-коду и
ссылкой на лог-строку — это код, на который нет статических ссылок (вызов
косвенный). Два прохода оформления до схождения:

1. вход — адрес в промежутке, на который есть ссылка типа CALL;
2. вход — инструкция сразу после конца функции (`j blink` или переход в
   эпилог милли-кода 0x8c02d4…0x8c0348 / 0x920224…0x9202a4), с пропуском слота
   задержки.

Итог: +533 функции, в перепись вошло ≈ 33 КБ кода; остаток вне функций —
14 294 Б в 990 кусках (в среднем 14 Б: выравнивание и обрывки). Побочный брак
второго правила: 131 вход поставлен на выравнивающий `nop_s` за два байта до
настоящего начала функции (2 920 Б).

В данных ucode таблиц имён автоматов и классов нет — только 16 имён модулей
лога по 0x8006d4; крупные блоки ucode именуются чтением кода.

Кандидаты на функции из данных ОЗУ фильтруются условием «адрес уже
дизассемблирован по потоку»: малые целые в данных (2, 4, 6, 8, …) иначе дают
ложные адреса (отсеяно 14 из 47 и 11 из 41 без потери настоящих целей). Кроме
`blob_uc_data` просканированы `blob_upper`, `blob_fw_peri`, `blob_rgf_ext`.

## 4. Динамическое покрытие **[железо]**

Смещения строк берутся прямо из колец лога (сопоставление по тексту занижает
результат: в разобранных строках подставлены значения — 4 % вместо 24 %).
За 481 снятое кольцо наблюдалось 614 строк из 2292 (27 %):

| действие | покрытие строк |
|---|---|
| обычная работа AP/STA | 13 % |
| сканирование | 24 %; `scan_mngr.cpp` 0 → 52 %, ожили `discovery.cpp`, `tx_probe.cpp` |
| режим обнаружения, IBSS, PBSS | 25 % |
| включение энергосбережения | ожили `PS_ASSOC_SM`, профиль питания, `awake peers vector = 0x0` |
| заведомо неверные команды WMI | 27 %; `wmi_handlers.cpp` 0 → 9/37 |

Без сканирования подсистемы поиска (`scan_mngr.cpp` 0/77, `find_mngr.cpp`,
`find_main_sm.cpp`, `psc_if.cpp`) не исполняются вовсе.

Пути проверки параметров WMI дали пределы, согласующиеся с таблицей РЧ-секторов:
`sector_idx` ∈ [0, 127] (128 секторов при шаге слота 0xc0), `cid` ∈ [0, 7],
`sector_type` — 0 (RX) или 1 (TX).

Функций `fw_code` с доказанным исполнением — 304 (46 836 Б, 24 % байт сегмента);
безымянных среди них нет — всё, что пишет в лог, названо по тем же строкам.
Ценность метрики — в списке мёртвых подсистем и способах их разбудить.

## 5. Объекты C++ в `fw_data`

Установщики таблиц методов находятся по образцу «несколько подряд
`mov rX,0x800xxx` + `st rX,[rY,N]`»:

| установщик | таблицы | объекты |
|---|---|---|
| 0x8c17e8 | 6 (0x8005a4…0x8006cc) | калибровки |
| 0x8c19bc | 4 (0x800758…0x8007cc) | менеджеры энергосбережения |
| 0x8c1938 | 3 (0x8006bc, 0x800718, 0x80084c) | не опознаны |
| 0x8c1838 | 2 (0x800878, 0x800880) | не опознаны |
| 0x8c19e4 | 2 (0x8005d4, 0x800634) | повторная установка калибровок |

**Калибровки.** 0x8c17e8 кладёт шесть указателей в таблицу по **0x8430b0** с шагом
12 Б; порядок установки — индекс объекта, имена — массив по **0x800d9c**: SAR,
BB_GAIN_DC, IF_GAIN, LO_LEAKAGE, SILENT_RSSI, LO_POWER. Соответствие
подтверждается независимо дважды: у объекта 1 (BB_GAIN_DC) в ячейке +0x28 —
`calib_bb_gain_dc::check_online_estimation_condition`, у объекта 5 (LO_POWER) в
+0x0c — `class_calib_lo_power::check_online_…`. Слоты таблицы методов —
[4.1/docs/MISC.md §1](https://github.com/klukonin/SparRAW-firmware/blob/main/4.1/docs/MISC.md).

**Менеджеры PS.** Строки опознаны по столбцу +0x08: `ps_assoc_mgr::set_awake_tsf`
и `ps_nonassoc_mgr::ps_evt_handler`.

**Периодические задачи.** Объекты с `periodic_service` в +0x00, собственным шагом
в +0x08 и именем файла рядом: `ka_necessity_detector`, `phy_monitor` и один
неопознанный.

## Не установлено

* Границы объектов `fw_data` в области таблиц методов: записи, похожие на массив
  с шагом 0x44, перекрываются с таблицами PS-менеджеров, таблицы 0x8c1938 — с
  таблицами калибровок; без разбора читающего кода границы не проводятся.
* Классы таблиц 0x8c1938 и 0x8c1838.
