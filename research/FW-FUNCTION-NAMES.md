# Имена функций fw из лог-строк: метод и свойства

Способ получения имён вида `class::method` для функций `fw_code` по лог-строкам прошивки и
перенос имён между сборками. Итоговые имена обеих версий — в деревьях `4.1/src/asm/fw/blocks.json`
и `6.2/src/asm/fw/blocks.json` репозитория прошивки; классы и синглтоны —
[docs/FW-OBJECTS.md](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/FW-OBJECTS.md);
классы доказанности имён при переносе 6.2 → 4.1 —
[4.1/docs/NAMES-FROM-62.md](https://github.com/klukonin/SparRAW-firmware/blob/main/4.1/docs/NAMES-FROM-62.md).

## 1. Источник строк **[код]**

Образы RouterOS несут таблицы строк лога в записях контейнера типов 100 (ucode) и 101 (fw)
([FIRMWARE-COMPARISON.md](FIRMWARE-COMPARISON.md)); в linux-firmware 5.2.0.18 их нет.
Таблица 101 образа 4.1.0.1000: 111 444 Б, 2296 строк, из них 615 вида `класс::метод`
(311 уникальных имён) и 119 имён исходных файлов.

## 2. Как код ссылается на строку **[код]**

* **ucode** адресует строку байтовым смещением в таблице: константа `offset | params`.
* **fw** адресует строку полным указателем на сегмент строк, отображённый на
  **VA 0x01000000** (та же база, что у `state_names`/`event_names` дескрипторов автоматов):
  `limm 0x01000000 | offset`. Длинный иммедиат ARC хранится с переставленными полусловами:
  `pack('<H', V >> 16) + pack('<H', V & 0xffff)`. Поиск по смещениям без базы даёт мусор.

Скан `fw_code` 4.1 по этому шаблону: 2511 ссылок в 805 функциях. Скан 6.2: 1555 лог-сайтов в 685
функциях, 360 функций с именем `class::method`.

Правила назначения имени:
* имя берётся из первой подходящей строки функции, поэтому часть имён описательные
  (по тексту строки), а не настоящие символы;
* строка, встречающаяся у более чем двух функций, считается тегом, а не именем;
* если строка — имя файла, функция получает только привязку к файлу
  (по 4.1 — 101 исходный файл).

## 3. Алфавитная раскладка функций **[код]**

Имена методов монотонно не убывают с ростом адреса: в 6.2 — 317 из 359 переходов (88,3 %),
самые длинные монотонные серии — 31/27/23/20 функций подряд. Линкер раскладывал функции по
имени, поэтому имя неизвестной функции ограничивается по алфавиту её соседями. Сбои монотонности
объясняются шумом привязки: функция ссылается на строку, называющую её вызывающего или
вызываемого (например, `wmi_handler_set_...::verify_inputs` перед
`..._get_selected_...::check_inputs_valid`), либо извлечено имя класса, а не метода
(`tof_mgr`, `ftm_mngr`).

## 4. Перенос имён на сборку 6.2.0.225 (UBNT) **[код]**

Прямой перенос по адресам невозможен: сборки 6.2.0.225 и 6.2.0.1000 разошлись (перекрытие
16-байтовых фрагментов ~3 %). Перенос — выравниванием последовательностей функций:

1. **Якоря из таблиц переходов автоматов.** У 17 совпавших автоматов каждая ячейка
   `state × event` хранит смещение функции-действия, позиционно одинаковое в обоих образах:
   172 сырых пары → 13 точных якорей после фильтра выбросов по наибольшей возрастающей
   подпоследовательности.
2. **Needleman–Wunsch с якорями** между упорядоченными списками функций (2359 в 6.2.0.225,
   2321 в 6.2.0.1000); мера сходства — относительная разница размеров функций, якоря — жёсткие
   границы сегментов.
3. Итог: 2040 пар соответствия, перенесено 285 имён.

| проверка | результат |
|---|---|
| пары функций-действий автоматов (эталон) | 6 верных, 0 ошибочных (2 не отобразились) |
| алфавитная монотонность перенесённых имён | 88,0 % (у исходной сборки 88,3 %) |
| линейная интерполяция (отвергнута) | 5 верных, 1 ошибка; медиана расхождения размеров 25 % |

Имена на 6.2.0.225 — производные (через выравнивание), а не прочитанные из собственных строк
образа.

## 6. Покрытие по факту исполнения **[железо]**

По 3300 снимкам колец лога на стенде (узлы AP и STA, сток и патч) наблюдалось 348 разных строк
fw — они доказывают исполнение 156 функций fw; для ucode — 20 строк и 8 функций. Все 156
функций fw получили имена.
