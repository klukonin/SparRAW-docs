# Окно AW: измерения и последствия снятия (4.1.0.1000)

Окно AW (в терминах 802.11ad — ATI) стоит между BHI и DTI. Механизм окна, гейт
`bi_ap_mon_if__trigger_bhi` (uc 0x930564) с тремя условиями, автомат BI и путь
длительности AW описаны в документации прошивки:
[docs/BEACONING.md §6](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/BEACONING.md#6-автомат-bi-и-окна),
[docs/STANDARD-MAPPING.md](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/STANDARD-MAPPING.md)
(разделы «Гейт окна AW» и «Путь длительности AW»),
[docs/MAC-COMMANDS.md, приложение В.1](https://github.com/klukonin/SparRAW-firmware/blob/main/docs/MAC-COMMANDS.md#в1-автомат-bi-микрокод-41).
Здесь — опыты на стенде: бюджет интервала, снятие окна тремя рычагами, влияние
на связь, обучение секторов и учёт сна.

Стенд: пара узлов AP + STA, BI = 100 TU = 102 400 мкс, без энергосбережения.
Записи в ОЗУ ucode — через debugfs `mem_write` (host-адреса `0x94xxxx`).

## 1. Бюджет интервала **[железо]**

Отчёт `MAC_MON` прошивки на каждом интервале:

```
MAC_MON [BTI] | start time 0x4ebc3ff9 | duration 1364
MAC_MON [AW ] | start time 0x4ebc454d | duration 1004
MAC_MON [DTI] | start time 0x4ebc4939 | duration 100032
```

12 интервалов подряд:

| окно | мин | макс | среднее | доля BI |
|---|---|---|---|---|
| BTI | 1364 | 1954 | 1561 | 1.5 % |
| AW | 1003 | 1006 | 1004 | 0.98 % |
| DTI | 99 442 | 100 032 | 99 835 | 97.5 % |

Сумма трёх окон в каждом интервале — ровно 102 400 мкс: окна делят
фиксированный бюджет.

В конфигурации без энергосбережения окно пустое: во всех отчётах
`backoff 1 | rx atim 0 | bcons_atim_fail_vec 0x0 | tx atim pass 0 | tx atim fail 0 |
tx atim counter 0`.

## 2. Три рычага снятия окна **[железо]**

| рычаг | ucode / host | значение | гейт |
|---|---|---|---|
| `bi_mode` (`bcon_kind`) | 0x801438 / 0x941438 | 2 | C |
| флаг A | 0x800458 / 0x940458 | 0 (в стоке 1) | A |
| флаг B | 0x80049c / 0x94049c | ≠ 0 (в стоке 0) | B |

Счётчики обработчиков окон (`bi_ap_mon__aw_event` → 0x801e1e,
`bi_ap_mon__dti_event` → 0x801e1c, `bi_ap_mon__bti_event` → 0x801e18) за 5 с:

| состояние | AW | DTI |
|---|---|---|
| сток | +49 | +49 |
| `0x800458 := 0` | +0 | +49 |
| возврат | +49 | +49 |
| `0x80049c := 1` | +0 | +49 |
| возврат | +49 | +49 |

При `bi_mode = 2` за 6 с трассы ucode: `AW EVENT` 0 (сток 5), `DTI EVENT` 5,
`PRE TBTT` 4; счётчик 0x801e1e стоит (0x0548 → 0x0548 за 4 с), 0x801e1c идёт
+39 за 4 с (≈ 1 на BI). После возврата `bi_mode = 1` оба счётчика
возобновляются. `bi_mode = 2` одновременно включает рандомизатор задержки маяка
(второй гейт на той же ячейке, в трассе появляются `randomize beacon` и
`set_tsf_event()`); для снятия AW без рандомизатора — флаги A/B.

Писателей ячеек 0x800458 и 0x80049c в коде ucode нет — ни через `gp`, ни по
абсолютному адресу.

## 3. Граница окна по TSF **[железо]**

Метки TSF событий ucode→fw 0x17 (PRE TBTT / `MAC_MONITOR_EVT`, открывает окно) и
0x16 (awake peers / `PS_AWAKE_PEER_EVT`, закрывает):

| состояние | TSF начала | TSF конца | окно |
|---|---|---|---|
| AW работает | 0x55a1e54e | 0x55a1e93f | 1009 мкс |
| AW работает | 0x55a3754d | 0x55a3793f | 1010 мкс |
| AW снято | 0x567e354f | 0x567e3554 | 5 мкс |
| AW снято | 0x567fc54f | 0x567fc554 | 5 мкс |

| состояние | окно AW (0x17→0x16) | остаток (0x16→0x17) | сумма |
|---|---|---|---|
| AW работает | 1009.6 мкс (n = 5) | 101 390.2 мкс (n = 4) | 102 399.9 |
| AW снято | 5.0 мкс (n = 4) | 102 395.3 мкс (n = 3) | 102 400.3 |

Окно сжимается на 1004.6 мкс, остаток интервала растёт на 1005.1 мкс:
освобождённое время достаётся DTI. Ожидаемый прирост эфирного времени —
1005 / 102 400 = 0.98 %, при ≈ 985 Мбит/с это ≈ +10 Мбит/с.

Шесть прогонов TCP по 10 с в каждом состоянии дали 963…985 Мбит/с без AW
против 977…989 с AW: разброс ±1.3 % больше ожидаемого эффекта, прирост этой
методикой не разрешается. Для разрешения нужна точность лучше ±0.5 % (длинные
прогоны, фиксированный размер пакета, отключённая адаптация скорости) либо
прямое измерение занятости эфира.

## 4. Побочный эффект: нули в `MAC_MON` **[код + железо]**

При снятом окне любым из трёх рычагов отчёт `MAC_MON` продолжает приходить
каждый интервал, но длительности в нём нулевые:

```
[BTI] | start time 0x00000000ab215ff9 | duration 0
[AW ] | start time 0x0000000000000000 | duration 0
[DTI] | start time 0x0000000000000000 | duration 0
```

Учётчик `bi_window_timing_update` (uc 0x921ce8) работает парой «засечка начала
(аргумент 0) — вычисление разности (аргумент 1)»; вызов с 0 стоит только на
ветке AW `bi_ap_mon_if__trigger_bhi`, вызов с 1 — на входе 4 диспетчера
триггеров. Без засечки длительности не считаются. Начало BTI берётся из другого
места и сохраняется. В этом состоянии окна измеряются только по меткам TSF
трассы ucode.

## 5. Связь при снятом окне **[железо]**

`bi_mode = 2` на 45–60 с (≈ 586 интервалов маяка):

| | станций | KA_cnt | KA_fail_cnt |
|---|---|---|---|
| сток | 1 | 5 | 0 |
| окно снято | 1 | 6 | 0 |
| возврат | 1 | 7 | 0 |

Станция остаётся ассоциированной, keep-alive проходят, DTI и `PRE TBTT` идут в
прежнем темпе, установившаяся пропускная способность не меняется.

## 6. Обучение секторов без окна **[железо]**

* Путь оценки переживает снятие окна: событие 0x16, в котором считается
  `bf_trigger`, при снятом окне приходит через 5 мкс после 0x17; в захватах
  поровну — по 5 событий `AWAKE PEERS` и по 5 строк с `bf_trigger` в обоих
  состояниях.
* По строкам прошивки развёртка завершается в BTI, A-BFT и DTI
  (`BF_SUBFLOWS_DONE_DTI_TXSS`, `BF_SUBFLOWS_DONE_ABFT_TXSS`,
  `BF_SUBFLOWS_DONE_DTI_TXSS_BRP`); окна AW среди них нет.
* Переассоциация в обоих состояниях:

| | подключилась | согласованная скорость | пропускная способность |
|---|---|---|---|
| AW снято | да | 2310 Мбит/с | 981, 986 Мбит/с |
| AW работает | да | 2310 Мбит/с | 985, 986 Мбит/с |

## 7. Что окно несёт: учёт сна **[железо]**

| | `awake peers vector` | `peer_eligibility` |
|---|---|---|
| AW работает | 0x1 | 0xff |
| AW снято | 0xff | 0xff |

С окном точка знает, что бодрствует один пир; без окна консервативно считает
бодрствующими всех восьмерых. Без энергосбережения это ни на что не влияет; в
сети со спящими станциями снятие AW ломает учёт сна, а не обучение секторов.

## Не установлено

* Назначение флагов A (0x800458) и B (0x80049c); по базе 0x800400, на которую
  ссылается `txrx_api_cmd_handler.c`, — поля структуры, заполняемой через
  указатель **[гипотеза]**.
* Прирост пропускной способности от снятия AW (ожидаемые 0.98 %) прямым
  измерением трафика.
